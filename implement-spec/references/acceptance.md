# 最终验收与 tracker 收尾

在整体 OCR 及修复完成后执行。主代理独占 ticket 写回与关闭，子代理只提供证据。

## 复验与人工确认

1. 重新读取 tracker 中每票的当前正文，以当前验收区的准确文本匹配已有证据。标准有新增或变化时重新验证；证据找不到对应标准时暂停该票写回并报告，不模糊匹配。
2. 在最终集成状态下重新执行所有可运行的验收验证，包括原先已勾选的项目，并运行项目全量测试与类型检查。记录命令、结果和所针对的提交；单票 worktree 的历史通过结果不能代替本轮复验。
3. 每项分为 `ran`（实际执行并观察通过）、`read`（仅通过阅读判断）或未通过/未验证。每个勾选须有一行证据，证据保留在会话输出和恢复记录中。测试不能运行时明确报告，不将其改列为仅需人工确认的已通过项目。
4. 按 ticket 一次汇总 `read` 项，请用户明确确认；确认前保持未勾选。此前明确确认且相关内容未变化的项目沿用确认。拒绝或未回答的项目保持未勾选。
5. 已有勾选对应的验证失败时撤勾并明确报告；此前已关闭的票若失去验收条件，按 tracker 规则重新打开并记录原因。新证据全部有效后才能重新关闭。

后续代码修复会使受影响的证据失效；在新集成状态重跑这些验收与项目最终检查。每张票均需非空验收区且全部通过，整份 spec 才具备交付条件。

## 正式写回

每次写入前重新读取正文，只修改验收区中按准确文本匹配的复选框，保留其他任务列表、正文和并发编辑。使用 tracker 的版本条件写入机制（若支持）；检测到并发变更时重新读取核对，不能用旧正文覆盖。

追加中文记录：关联提交与分支、执行通过的项目、用户确认项、撤勾原因和待完成项。完整命令与证据留在会话/恢复记录，票上保留简短摘要。即使仍有待确认项，也可写回已验证状态；交付门槛仍要求全部通过。

### 外部 tracker

先确保代码和修复已经提交，再写回。正文更新或评论追加任一步失败即暂停后续写回及交付，说明哪些已成功、哪些尚未完成；保留已产生的提交与远端记录。恢复时核对现状，只补未完成动作。

### 仓库内 Markdown tickets

将全部票的验收修改及必要日志作为独立中文 Conventional Commit 收尾，保留原有代码提交。预先保存本次将修改的验收区和日志片段；提交失败时仅还原本次未提交的写回，不碰用户已有修改。

还原前比较当前片段与本次写入后的片段：仍一致才执行反向还原；已被用户或其他进程改动则保留现场并报告冲突，不能直接回填旧内容。

遵守用户已有暂存集合：其中存在不属于本次收尾的内容时，暂停收尾提交并报告，不能混入或撤出这些内容。钩子自动修复时仅重试一次；拒绝时保留代码提交，报告失败。

## 交付

所有票全部通过、写回成功且最终工作已提交后：

- **有 PR**：推送集成分支，再将草稿 PR 转为待审查。由 PR 流程关闭 spec/tickets，此时报告“待合并”，不提前手动关闭。若本地 tracker 有独立关闭状态，验收提交仅记录通过，关闭仍遵循配置的 PR 工作流。
- **无 PR**：有远端则先推送成功，再按配置关闭全部 tickets 和 spec；无远端则明确报告跳过推送，继续本地关闭。首次推送按配置设置 upstream。推送被拒绝时停止交付，保留分支和开放的票，不强推或改写历史。
- **本地关闭需改文件**：先确保验收提交已经落地且已推送（有远端时），再单独提交本地关闭状态并推送。关闭提交或其推送失败时报告本地与远端的具体差异，保留恢复材料，暂不宣称交付完成。

失败不等于全部回滚：已提交的代码、已写回的远端状态保留并逐项说明；只回滚尚未提交且属于本次的本地票据编辑。重试前读取当前状态，避免重复评论、重复关闭或覆盖新修改。
